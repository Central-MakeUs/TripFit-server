# 여행방 나가기·내보내기·삭제·회원 탈퇴 — 구현 규칙

TripFit 프론트엔드 저장소에서 "방을 떠나는" 네 가지 액션(참여자 나가기·방장의 참여자 내보내기·방 삭제·회원 탈퇴)을 구현·수정할 때 아래 규칙을 따르라. 여기 없는 세부 계약은 추측하지 말고 사용자에게 확인하라.

모든 API 응답은 `{ "data": {...}, "message": "...", "code": "..." }` envelope로 온다. 성공 시 본문이 없는 API는 `204 No Content`로만 응답한다고 가정하고 파싱 코드를 짜라.

**여행방 상태**: `ONGOING`(조율 중) → `CONFIRMED`(일정 확정) → `EXPIRED`(만료). `CONFIRMED`는 `ONGOING`으로 되돌아갈 수 있다(확정 취소). "취소됨"을 뜻하는 별도 상태가 있다고 가정하지 마라 — 방 삭제는 상태 전이가 아니라 소프트 삭제(목록에서 제외)로 구현돼 있다.

> ⚠️ **먼저 확인하라**: 아래 4개 액션(나가기·내보내기·삭제·탈퇴)은 전부 호출 가능한 API로 존재한다. 다만 **`CONFIRMED` 상태 자체와 "일정 확정/확정 취소" API는 아직 없다** — 지금 시점에는 방이 `ONGOING`이거나 `EXPIRED`인 경우만 실제로 발생한다고 가정하고 구현하라. 아래 표의 `CONFIRMED` 열을 지금 당장 동작하는 것처럼 테스트 코드를 짜지 마라. 확정 기능이 배포된다는 공지가 오기 전까지는 목표 동작 참고용으로만 취급하라.

> ⚠️ **2026-08-19 변경 — 나가기도 「방에 입장한 뒤」에만 가능하다.** 여행방은 `join`(또는 방 생성) 직후 **미입장(`SCHEDULE_PENDING`)** 상태이고, 사전 일정 입력 플로우를 마쳐 `activate`를 호출해야 입장(`ACTIVE`)이 된다. **미입장 상태에서 `DELETE /trips/{tripId}/members/me`를 부르면 403 `SCHEDULE_ACTIVATION_REQUIRED`가 온다.** 방 안 화면 자체가 열리지 않는 상태이므로 나가기 버튼을 그 경로에 노출하지 마라 — 미입장자가 방에서 빠지는 길은 ① 일정 입력을 마쳐 입장한 뒤 나가기 ② **방장이 내보내기** 두 개다. 판정은 홈 카드·상세 응답의 `myMemberStatus`로 하라.

## 규칙 1 — 네 액션을 서로 다른 화면/버튼으로 분리해서 구현하라

| 액션 | 누가 호출 | UI에 넣을 때 주의 |
|---|---|---|
| **방 나가기** | 참여자(MEMBER) 본인 · **입장(`ACTIVE`) 이후만** | 방장 계정에는 이 버튼을 노출하지 마라(무조건 에러). `myMemberStatus === 'SCHEDULE_PENDING'`인 방에서도 노출하지 마라 — 403이 온다 |
| **참여자 내보내기** | 방장(OWNER) | **반드시 구현하라** — 미입장자가 잡아둔 정원 자리를 비우는 **유일한 수단**이다(아래 규칙 7). 멤버 목록 화면에서만 노출하고, 방 상태가 `ONGOING`이 아니면 버튼을 비활성화하라 |
| **방 삭제** | 방장(OWNER) | 방 상태와 무관하게 항상 노출 가능 |
| **회원 탈퇴** | 사용자 본인 | 마이페이지/설정 화면에 두고, "진행 중인 방이 있으면 차단"하는 확인 로직을 넣지 마라(아래 규칙 4) |

방장 위임(ownership transfer) UI를 만들지 마라 — 그런 API가 없다. 방장이 방을 넘기고 싶어 하는 상황이면 "방 삭제"로 안내하라.

## 규칙 2 — 상태별 허용 여부를 다음 표대로 프론트 게이트에 반영하라

| 액션 | ONGOING | CONFIRMED* | EXPIRED |
|---|---|---|---|
| 참여자 → 방 나가기 (**`ACTIVE`일 때만**) | 허용 | 허용(즉시 반영) | 허용 |
| 방장 → 참여자 내보내기 | 허용 | 차단 | 차단 |
| 방장 → 방 삭제 | 허용 | 허용 | 허용 |
| 회원 탈퇴(참여자 입장) | 허용(자동 나가기) | 허용 | 허용 |
| 회원 탈퇴(방장 입장) | 허용(자동 삭제) | 허용 | 허용 |

\* `CONFIRMED` 행은 위 경고 참고 — 지금은 발생하지 않는다.

구현 시 다음 패턴을 코드에 반영하라: **"나가기"와 "삭제"는 여행방 상태 체크 없이 항상 버튼을 활성화하라. "참여자 내보내기"만 `status !== 'ONGOING'`이면 버튼을 비활성화하거나 숨겨라.** 이 세 액션에 동일한 상태 체크 함수를 재사용하지 마라 — 조건이 다르다.

**여행방 상태(`status`)와 내 멤버 상태(`myMemberStatus`)는 다른 축이다.** 위 표는 여행방 상태만 다룬다. 나가기에는 **추가로** `myMemberStatus === 'ACTIVE'` 조건이 붙는다(2026-08-19) — 두 값을 하나의 체크 함수에 섞지 마라.

## 규칙 3 — `CONFIRMED` 관련 기능은 나중에 구현하되, 지금 아래를 가정하고 설계하라

확정 기능이 나중에 배포되면 다음 동작을 전제로 화면이 동작해야 한다. 지금 미리 구조를 잡을 때 참고하라:

- 참여자가 확정된 방에서 나가도, **이미 확정된 일정·추천 결과·캘린더 화면은 그대로 유지**돼야 한다 — 나간 사람을 캘린더/멤버 목록에서 즉시 지우는 로직을 만들지 마라. 확정 스냅샷은 다른 멤버 화면에서 그대로 보여야 한다.
- "확정 취소" 액션이 호출된 시점에야 스냅샷이 폐기되고 최신 멤버 구성으로 다시 계산된다 — 즉 "누가 나갔는지"와 "화면에 언제 반영되는지"를 분리해서 설계하라.
- "확정 취소"는 되돌릴 수 없는 별도 종료 상태로 가지 않는다. 단순히 `ONGOING`으로 복귀하는 것으로 구현하라 — "취소됨" 상태를 위한 별도 UI(배지, 필터 등)를 만들지 마라.

## 규칙 4 — 회원 탈퇴 화면에 차단 로직을 넣지 마라

- "진행 중인 방이 있으니 먼저 정리하세요" 같은 차단 모달·검증을 만들지 마라 — 탈퇴는 어떤 경우에도 막히지 않는다.
- 참여자로 있던 방은 상태와 무관하게 자동으로 나가기 처리된다고 가정하고, 탈퇴 확인 문구에 "참여 중인 방에서 자동으로 나가게 됩니다" 정도만 안내하라.
- 방장으로 있던 방은 상태와 무관하게 자동으로 삭제 처리된다고 가정하라. **탈퇴 확인 모달에 "방장으로 있는 방은 모두 삭제되며 다른 참여자도 더 이상 볼 수 없습니다"라는 경고 문구를 반드시 넣어라** — 이건 사용자가 오해하기 쉬운 지점이다.
- 탈퇴 처리 후 같은 계정으로 재로그인하면 서버가 차단하지 않고 기존 계정을 그대로 부활시켜 로그인시킨다고 가정하라 — 전용 에러 처리 분기를 만들 필요 없다(아래 규칙 6).

## 규칙 5 — 관련 API는 아래 표만 사용하라

| Method | Path | 인증 | 설명 |
|---|---|---|---|
| `DELETE` | `/api/v1/trips/{tripId}/members/me` | JWT + **이 방 `ACTIVE`** | 참여자 본인이 방 나가기. 성공 시 `204 No Content`. 미입장이면 403 `SCHEDULE_ACTIVATION_REQUIRED` |
| `DELETE` | `/api/v1/trips/{tripId}/members/{userId}` | JWT + 방장 | 방장이 특정 멤버 내보내기(`ONGOING`만). **대상의 `memberStatus`는 보지 않는다 — 미입장자도 내보낼 수 있다.** 성공 시 갱신된 멤버 목록(`200`) |
| `DELETE` | `/api/v1/trips/{tripId}` | JWT + 방장 | 방 삭제(소프트). 성공 시 `204 No Content` |
| `DELETE` | `/api/v1/users/me` | JWT | 회원 탈퇴. 참여/소유 방 자동 정리 후 처리. 성공 시 `204 No Content` |

에러 코드를 처리할 때 아래 표를 그대로 매핑하라. 표에 없는 코드가 오면 임의로 의미를 추측하지 말고 사용자에게 물어라.

| HTTP | code | 상황 | 처리 |
|---|---|---|---|
| 400 | `TRIP_OWNER_CANNOT_LEAVE` | 방장이 "방 나가기" API를 호출함 | 방 삭제로 안내하라 |
| 403 | `TRIP_ACCESS_DENIED` | 이 방의 멤버가 아니거나 이미 나간 상태에서 재호출 | 목록 새로고침 후 재시도 안내 |
| 403 | `SCHEDULE_ACTIVATION_REQUIRED` | **미입장(`SCHEDULE_PENDING`) 상태에서 나가기 호출** (2026-08-19 신규) | 나가기 버튼을 그 상태에 노출한 것 자체가 버그다 — 일정 입력 플로우로 보내라 |
| 403 | `TRIP_FORBIDDEN` | 방장이 아닌 사람이 내보내기·삭제 시도 | 권한 없음 안내 |
| 400 | `CANNOT_REMOVE_OWNER` | 방장을 내보내기 대상으로 지정 | 멤버 목록 UI에서 방장은 내보내기 버튼 자체를 숨겨서 이 케이스를 방지하라 |
| 404 | `TRIP_NOT_FOUND` | 존재하지 않거나 이미 삭제된 방 | 목록으로 되돌리기 |
| 404 | `TRIP_MEMBER_NOT_FOUND` | 내보내기 대상 멤버가 없음(이미 나감 포함) | 멤버 목록 새로고침 |
| 409 | `TRIP_NOT_ONGOING` | `CONFIRMED`/`EXPIRED` 상태에서 참여자 내보내기 시도 | 규칙 2의 버튼 비활성화가 정상 동작했다면 실사용 중 거의 나오지 않아야 한다 |

탈퇴한 계정으로 재로그인하는 경우는 **에러가 아니다** — 아래 규칙 6 참고.

## 규칙 6 — 재가입 관련 UI는 다음 기준으로 만들어라

- 나가거나 내보내진 멤버가 같은 초대 링크로 다시 참여하려는 경우는 **막지 마라** — 별도 차단 로직 없이 그냥 참여 플로우를 다시 태우면 된다.
- **탈퇴한 계정의 재가입 정책은 확정됐다(2026-07-27): 무조건 재가입 가능.** 같은 소셜 계정으로 다시 로그인하면 서버가 차단하지 않고 기존(soft-deleted) 계정을 그대로 부활시켜 로그인을 진행한다 — 전용 에러 코드도 전용 UI도 없다. "탈퇴 후 다시 가입하기" 같은 별도 화면을 만들지 마라.
- 부활 후에는 `firstName`/`lastName`/`isGoogleCalendarConnected`가 탈퇴 시점에 초기화된 채로 로그인 응답이 온다 — 즉 이름이 `null`인 신규 가입자와 서버 응답 형태가 동일하다. `user-onboarding.md` 규칙 2의 이름 게이트를 그대로 타면 재온보딩이 자연스럽게 처리되므로, 재가입임을 감지하는 별도 로직을 만들지 마라. "다시 가입하신 것을 환영합니다" 같은 전용 안내가 필요하면, 그 값을 구분할 필드가 현재 응답에 없다는 것을 먼저 사용자에게 확인하라.

## 규칙 7 — 방장 화면에 「내보내기」를 반드시 넣어라 (미입장자 자리 회수)

`join` 직후부터 정원 한 자리가 차기 때문에, 초대 링크만 열고 일정 입력을 하지 않은 사람이 자리를 계속 점유한다. 서버는 그 자리를 **자동으로 회수하지 않고**(TTL·배치 없음), 본인도 미입장 상태에서는 나갈 수 없다. 즉 **방장의 내보내기가 유일한 회수 수단**이다.

- 멤버 목록 화면에서 각 멤버의 **`memberStatus`** 를 보여줘라(`ACTIVE` / `SCHEDULE_PENDING`). 방장이 "아직 일정 확인 안 한 사람"을 식별할 수 있어야 내보낼 대상을 고를 수 있다.
- 정원이 다 찼는데 `activeMemberCount < memberCount`이면(= 미입장자가 자리를 잡고 있음) 새 참여자는 `409 TRIP_MEMBER_FULL`로 막힌다. 이 상태에서 방장에게 **"일정 확인을 안 한 참여자를 내보내면 자리가 생깁니다"** 를 안내하라.
- 응답률(`memberFillRate`)이 100%에 도달하지 않고 "전원 제출 완료" 알림도 오지 않는 원인이 대개 이것이다 — 방장이 원인을 알 수 있게 화면에 드러내라.
- 내보낸 멤버는 같은 초대 코드로 **다시 참여할 수 있다**(규칙 6) — "영구 차단"으로 안내하지 마라.
