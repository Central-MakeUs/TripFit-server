# 개별 일정 오버라이드 — 유저 시나리오 (프론트 공유용)

> 이 문서는 [`schedule-slot-override.md`](../../../specs/schedule-slot-override.md)(O1.4, API 계약 SSOT)와 [`schedule-calendar-merge.md`](schedule-calendar-merge.md)(구현 규칙)에서 **"유저가 실제로 뭘 보고, 뭘 누르고, 그 다음 뭐가 보이는지"** 만 뽑아 이야기 형태로 정리한 자료다. API 필드·에러 코드의 정확한 계약은 위 두 문서가 SSOT이고, 이 문서는 **정합이 깨지면 안 된다** — 값이 다르면 이 문서가 틀린 것이니 스펙을 기준으로 고쳐라.
>
> 대상 독자: 프론트엔드. 목적: "왜 이렇게 동작해야 하는지"를 화면 흐름으로 이해시키는 것.

## 등장인물 — 유저 A

**유저 A**는 평일에 출근하는 직장인이다. TripFit 마이페이지에 정기 일정을 두 개 등록해뒀다.

| ID | 이름 | 요일 | 시간 | 계산되는 슬롯(그 요일에 매칭될 때) |
|----|------|------|------|-----------------------------------|
| R1 | 출근 | 월·화·수·목·금 | 09:00~18:00 | 아침 **불가능** / 오후 **불가능** / 저녁 **가능** |
| R2 | 저녁 수업 | 수 | 19:00~21:00 | 아침 가능 / 오후 가능 / 저녁 **불가능** |

시나리오의 배경 날짜는 **2026년 8월**이다. 8/3(월)~8/7(금)은 평일, 8/1·8/2·8/8·8/9는 주말. **8/5(수)만 R1·R2 둘 다 겹치는 날**이라 아침·오후·저녁이 전부 불가능하게 계산된다(슬롯별로 하나라도 정기가 "불가능"이라 하면 "불가능"이 이긴다 — 정기끼리 겹칠 때의 규칙, 이 문서의 주제는 아님).

이 문서의 각 시나리오는 **바로 앞 시나리오가 끝난 상태에서 이어진다** — 순서대로 읽어야 DB 상태가 맞다. 다만 "구글 캘린더" 절과 "여행방 멤버 달력" 절은 별도로 표시된 지점부터 새로 시작한다.

## 읽는 법

시나리오마다 3단계로 적는다.

1. **① 캘린더 조회 (수정 전)** — 유저 A가 마이페이지 캘린더 화면을 열었을 때 서버가 뭘 내려주는지, 화면에 어떻게 찍히는지
2. **② 수정** — 유저 A가 날짜를 눌러 바텀시트에서 뭘 바꾸고 저장하는지 (`PATCH` 요청)
3. **③ 결과 — 캘린더는 이제 이렇게 보여야 한다** — 저장 직후 응답 + 다시 캘린더를 조회했을 때 화면 표시

---

## 1부 — 부분 오버라이드의 핵심 동작

### 시나리오 1. 아무것도 안 건드린 상태 — 정기만 반영된 한 주

유저 A가 처음으로 마이페이지 캘린더를 연다. 아직 개별 일정을 한 번도 등록한 적이 없다.

**① 캘린더 조회 (수정 전)**

`GET /users/schedule/calendar?startDate=2026-08-03&endDate=2026-08-09`

```json
{
  "data": {
    "days": [
      {
        "date": "2026-08-03",
        "morningStatus": "IMPOSSIBLE",
        "afternoonStatus": "IMPOSSIBLE",
        "eveningStatus": "POSSIBLE",
        "uncertain": false
      },
      {
        "date": "2026-08-04",
        "morningStatus": "IMPOSSIBLE",
        "afternoonStatus": "IMPOSSIBLE",
        "eveningStatus": "POSSIBLE",
        "uncertain": false
      },
      {
        "date": "2026-08-05",
        "morningStatus": "IMPOSSIBLE",
        "afternoonStatus": "IMPOSSIBLE",
        "eveningStatus": "IMPOSSIBLE",
        "uncertain": false
      },
      {
        "date": "2026-08-06",
        "morningStatus": "IMPOSSIBLE",
        "afternoonStatus": "IMPOSSIBLE",
        "eveningStatus": "POSSIBLE",
        "uncertain": false
      },
      {
        "date": "2026-08-07",
        "morningStatus": "IMPOSSIBLE",
        "afternoonStatus": "IMPOSSIBLE",
        "eveningStatus": "POSSIBLE",
        "uncertain": false
      }
    ]
  }
}
```

**캘린더 UI:** 8/3~8/7은 정기(R1) 값이 그대로 찍힌다 — "개별로 손댄 적 없는 날"과 "정기값이 이렇게 계산된 날"을 화면상으로 구분할 방법은 없다(서버가 출처를 안 내려준다). 8/5만 하루 종일 불가능하게 보인다. **8/1·8/2·8/8·8/9(주말)는 응답 자체에 없다** — 정기도 개별도 구글도 아무 신호가 없기 때문이다. 이 날짜들은 "미입력"으로 그려야 한다. "가능(POSSIBLE)"으로 착각해서 초록 점을 찍으면 안 된다.

**② 수정 / ③ 결과 — 이번 시나리오는 없음.** 아직 아무것도 바꾸지 않은 기준선(baseline)이다.

---

### 시나리오 2. 오후 반차 — 슬롯 하나만 바꾸고 싶은데 왜 3개를 다 보내야 하나

8/6(목)에 오후 반차를 써서 오후만 여행 가능하게 만들고 싶다. 유저 A가 8/6을 누른다.

**① 캘린더 조회 (수정 전) — 바텀시트 프리필**

바텀시트는 시나리오 1의 `GET calendar` 값으로 프리필된다: 아침 불가능 / 오후 불가능 / 저녁 가능. 화면에는 이미 세 개의 슬롯 버튼이 그 상태로 눌려 있는 채로 열린다.

**② 수정**

유저 A는 오후 버튼만 눌러 "가능"으로 바꾼다. 아침·저녁은 건드리지 않는다. 저장 버튼을 누르면 프론트는 **화면에 지금 표시되고 있는 값 3개를 전부** 담아 보낸다 — 안 건드린 슬롯도 예외 없이 같이 보내야 한다.

`PATCH /users/schedule/personal`

```json
{
  "items": [
    {
      "scheduleDate": "2026-08-06",
      "slots": {
        "morningStatus": "IMPOSSIBLE",
        "afternoonStatus": "POSSIBLE",
        "eveningStatus": "POSSIBLE"
      }
    }
  ]
}
```

> **왜 3개 다 보내야 하나:** O1.4에서 `slots`는 "있으면 3개 전부 필수, 없으면 아예 필드 자체를 생략"이라는 계약이다. `slots` 안에 있는 슬롯 하나만 골라 나머지를 `null`로 보내는 건 **허용되지 않는다.** 슬롯을 하나라도 건드리는 순간 그 날짜의 슬롯 3개는 전부 오버라이드로 새로 확정된다고 생각하라.

**③ 결과 — 캘린더는 이제 이렇게 보여야 한다**

`PATCH` 응답:

```json
{
  "data": {
    "items": [
      {
        "id": "e1000000-...0001",
        "scheduleDate": "2026-08-06",
        "morningStatus": "IMPOSSIBLE",
        "afternoonStatus": "POSSIBLE",
        "eveningStatus": "POSSIBLE",
        "uncertain": false
      }
    ]
  }
}
```

다시 `GET calendar`를 호출해도 완전히 같은 값이 나온다. **캘린더 UI:** 8/6은 이제 오후에 "가능" 점이 새로 찍힌다. 아침·저녁은 눈으로 보기엔 시나리오 1과 똑같다 — 하지만 내부적으로는 이제 "정기값을 그대로 재전송해서 우연히 같은 값이 된 오버라이드"다. 이 차이는 화면에 안 보이지만 **시나리오 8**에서 실제로 드러난다.

---

### 시나리오 3. 갑자기 하루 종일 불가능 — 전체 오버라이드

시나리오 2에 이어서, 8/6에 급한 회식이 잡혀 하루 종일 불가능으로 바꾼다.

**① 캘린더 조회 (수정 전):** 시나리오 2의 결과(아침 불가능 / 오후 가능 / 저녁 가능)로 프리필.

**② 수정:** 세 버튼 다 "불가능"으로 바꾸고 저장.

```json
{
  "items": [
    {
      "scheduleDate": "2026-08-06",
      "slots": {
        "morningStatus": "IMPOSSIBLE",
        "afternoonStatus": "IMPOSSIBLE",
        "eveningStatus": "IMPOSSIBLE"
      }
    }
  ]
}
```

**③ 결과:** 8/6 전체가 "불가능"으로 바뀐다. 저녁은 정기(R1)가 "가능"이라고 계산하지만, **개별 오버라이드가 항상 이긴다** — 저녁도 예외 없이 "불가능"으로 찍힌다.

## 2부 — "일정이 바뀔 수도 있어요" (uncertain)

### 시나리오 4. uncertain을 켜도 오후 오버라이드는 사라지지 않는다

시나리오 2 상태(8/6: 오후만 가능으로 오버라이드, 나머지 시나리오 3은 없었다고 가정하고 다시 시작)로 돌아온다. 유저 A는 아직 오후 반차가 확정이 아니라서 "이 날 일정이 바뀔 수도 있어요" 토글을 켠다. 이 토글은 슬롯 버튼과 **완전히 별개의 스위치**다.

**① 캘린더 조회 (수정 전):** 8/6 = 아침 불가능 / 오후 가능 / 저녁 가능, uncertain 꺼짐.

**② 수정 — 토글만 ON**

```json
{
  "items": [
    {
      "scheduleDate": "2026-08-06",
      "uncertain": true
    }
  ]
}
```

`slots` 필드 자체를 아예 안 보낸다 — 슬롯 값을 바꾸는 게 아니라 uncertain만 바꾸는 것이기 때문이다.

**③ 결과 — 캘린더는 이제 이렇게 보여야 한다**

```json
{
  "date": "2026-08-06",
  "morningStatus": "IMPOSSIBLE",
  "afternoonStatus": "POSSIBLE",
  "eveningStatus": "POSSIBLE",
  "uncertain": true
}
```

슬롯 값은 토글 켜기 전과 **완전히 동일**하다 — 아침 불가능 / 오후 가능 / 저녁 가능. **캘린더 UI:** `uncertain: true`를 받으면 그 날짜를 다시 열었을 때 아침/오후/저녁 슬롯 버튼을 **비활성화(block)** 해야 한다 — 유저는 "불확실해요" 상태인 동안 슬롯을 편집할 수 없다.

### 시나리오 5. uncertain을 꺼도 오후 오버라이드가 다시 나타난다

시나리오 4에 이어서, 오후 반차가 확정돼 유저 A가 다시 toggle을 끈다.

**① 캘린더 조회 (수정 전):** 시나리오 4 결과 그대로(슬롯 버튼은 비활성 상태로 보임).

**② 수정**

```json
{
  "items": [
    {
      "scheduleDate": "2026-08-06",
      "uncertain": false
    }
  ]
}
```

**③ 결과:** 슬롯 값은 시나리오 2와 완전히 동일하게 복귀한다(아침 불가능 / 오후 가능 / 저녁 가능). **오후 오버라이드는 토글이 켜져 있던 동안 단 한 번도 사라지지 않았다** — 어딘가에 그대로 저장돼 있었을 뿐이다. **캘린더 UI:** 슬롯 버튼이 다시 활성화되고, 눌러보면 켜기 전에 유저가 저장했던 값 그대로 보인다.

> **여기서 흔히 하는 실수:** "uncertain 토글 = 슬롯 초기화"라고 착각하지 마라. 이 둘은 완전히 다른 필드이고, 서버는 `uncertain`만 온 요청에서 슬롯 컬럼을 **절대 건드리지 않는다.**

### 시나리오 6. uncertain과 슬롯을 한 번에 같이 바꾸기

시나리오 5 상태(uncertain 꺼짐, 오후 가능)에서, 유저 A가 오후 반차를 취소하고 대신 "그래도 하루 확정은 아니에요"라며 다시 불확실 토글도 켠다 — 슬롯과 uncertain을 **한 번의 저장으로 동시에** 바꾼다.

**② 수정**

```json
{
  "items": [
    {
      "scheduleDate": "2026-08-06",
      "slots": {
        "morningStatus": "IMPOSSIBLE",
        "afternoonStatus": "IMPOSSIBLE",
        "eveningStatus": "POSSIBLE"
      },
      "uncertain": true
    }
  ]
}
```

**③ 결과:** 슬롯 3개와 uncertain이 한 번의 요청, 한 개의 `items` 원소로 전부 반영된다. 아이템을 2개로 쪼개 보낼 필요가 없다 — "슬롯 변경용 아이템 하나 + uncertain 변경용 아이템 하나"처럼 나누면 오히려 **같은 날짜가 배열에 중복**돼 에러가 난다(시나리오 15 참고).

## 3부 — 정보가 없는 날 / 구글 캘린더

### 시나리오 7. 주말 — 아무 정보도 없으면 캘린더에 아예 안 나온다

**① 캘린더 조회:** `GET calendar?startDate=2026-08-08&endDate=2026-08-09`

```json
{
  "data": {
    "startDate": "2026-08-08",
    "endDate": "2026-08-09",
    "days": []
  }
}
```

**캘린더 UI:** `days` 배열이 비어 있다. 8/8·8/9는 정기도 없고(주말), 개별도 없고, 구글도 연동 안 된 상태라 **완전히 생략**된다. 이 상태를 "가능"도 "불가능"도 아닌 **"미입력"**으로 그려야 한다.

### 시나리오 8. 구글 캘린더를 연동하면 주말도 채워진다

8/8(토)은 정기가 없지만, 유저 A가 구글 캘린더에 "가족 모임"(오후)을 등록해뒀고 TripFit과 이미 연동돼 있다.

**① 캘린더 조회 (수정 전, 개별 오버라이드는 아직 없음):**

```json
{
  "date": "2026-08-08",
  "morningStatus": "POSSIBLE",
  "afternoonStatus": "IMPOSSIBLE",
  "eveningStatus": "POSSIBLE",
  "uncertain": false
}
```

**캘린더 UI:** 정기 매칭이 없는 주말인데도 이제 8/8이 나타난다 — 구글 신호 하나만으로도 "미입력"에서 벗어난다. 오후만 불가능하게 찍힌다.

**② 수정:** 유저 A가 "가족 모임은 저녁으로 옮겼으니 오후엔 여행 갈 수 있다"며 오후를 직접 가능으로 바꾼다.

```json
{
  "items": [
    {
      "scheduleDate": "2026-08-08",
      "slots": {
        "morningStatus": "POSSIBLE",
        "afternoonStatus": "POSSIBLE",
        "eveningStatus": "POSSIBLE"
      }
    }
  ]
}
```

**③ 결과:** 8/8 전체 가능. **개별 오버라이드는 구글 신호까지 포함한 자동 계산 결과 전체를 이긴다** — 구글이 오후를 busy로 보든 말든 상관없다.

### 시나리오 9. 구글 연동을 끊어도 이미 저장된 개별 오버라이드는 안 사라진다

시나리오 8에 이어, 유저 A가 구글 캘린더 연동을 해제한다.

**② 수정:** `DELETE /api/v1/users/google-calendar`

**③ 결과:** 구글 쪽 데이터만 삭제되고, 8/8의 개별 오버라이드(가능/가능/가능)와 정기 패턴은 **전혀 건드리지 않는다.** 다시 캘린더를 조회하면 8/8은 여전히 "가능"으로 나온다 — 단지 이제 그 값에 구글의 영향력이 없을 뿐이다(애초에 개별이 이겼으므로 결과는 연동 여부와 무관하게 같다).

## 4부 — 여행방 멤버 달력

### 시나리오 10. 여행방 멤버 화면에서도 내 캘린더와 똑같이 보여야 한다

유저 A가 참여 중인 여행방의 희망 기간이 8/6을 포함한다.

**① 조회:** `GET /trips/{tripId}/members/schedule-calendar`

**캘린더 UI:** 유저 A 항목의 8/6 값은 마이페이지 캘린더에서 본 값과 **한 글자도 다르지 않아야 한다.** 여행방 멤버 화면이 자체적으로 다른 병합 규칙을 쓰면 안 된다 — 프론트가 두 화면에서 색이 다르게 보이면 버그다.

## 5부 — 정기 패턴을 나중에 바꾸면 어떻게 되나 (트레이드오프)

### 시나리오 11. 오버라이드된 날짜는 정기가 바뀌어도 안 따라간다

유저 A가 오후 근무시간을 바꿔서 정기 패턴 R1을 "09:00~13:00"로 수정한다(`PATCH /users/schedule/regular/{R1_id}`). 8/3은 시나리오 2와 같은 방식으로 예전에 "아침만 가능"으로 오버라이드해둔 상태고, 8/4는 한 번도 손댄 적이 없다.

**③ 결과 — 두 날짜를 비교**

8/3(오버라이드 있음):

```json
{
  "date": "2026-08-03",
  "morningStatus": "POSSIBLE",
  "afternoonStatus": "IMPOSSIBLE",
  "eveningStatus": "IMPOSSIBLE",
  "uncertain": false
}
```

8/4(오버라이드 없음):

```json
{
  "date": "2026-08-04",
  "morningStatus": "IMPOSSIBLE",
  "afternoonStatus": "POSSIBLE",
  "eveningStatus": "POSSIBLE",
  "uncertain": false
}
```

**캘린더 UI:** 8/4(오버라이드 없음)는 새 근무시간(09~13시)이 바로 반영돼 오후가 가능해진다. 하지만 **8/3은 그대로다** — 예전에 저장해둔 오버라이드 값이 새 정기 패턴을 따라가지 않는다.

> **이걸 꼭 유저에게 알려줘야 한다:** 개별 캘린더에서 날짜 하나를 한 번이라도 저장하면, 그 날짜의 슬롯 3개는 **이후 정기 패턴이 바뀌어도 계속 그 값으로 고정**된다. 그리고 이걸 "정기값으로 되돌리는" 버튼이나 API는 **없다.** 되돌리고 싶으면 유저가 직접 그 날짜를 열어 원하는 값으로 다시 저장해야 한다.

### 시나리오 12. "오늘은 그냥 하루 종일 가능해요" — 예전에 있었던 버그가 지금은 없다

시나리오 11 상태(8/3: 가능/불가능/불가능으로 고정)에서, 유저 A가 "오늘은 하루 종일 여행 갈 수 있어요"라며 슬롯 3개를 전부 "가능"으로 바꿔 저장한다.

**② 수정**

```json
{
  "items": [
    {
      "scheduleDate": "2026-08-03",
      "slots": {
        "morningStatus": "POSSIBLE",
        "afternoonStatus": "POSSIBLE",
        "eveningStatus": "POSSIBLE"
      }
    }
  ]
}
```

**③ 결과:** 8/3 전체가 "가능"으로 저장되고, 이후 정기 패턴이 또 바뀌어도 이 값은 그대로 유지된다.

> **왜 굳이 이 시나리오를 문서에 남기나:** 예전 설계(O1.3)에서는 "슬롯 3개 다 가능 + uncertain 꺼짐"이라는 값 조합 자체를 "오버라이드 삭제 신호"로 착각해서, 유저가 방금 명시적으로 선언한 값이 조용히 사라지고 정기값으로 되돌아가는 버그가 있었다. **지금(O1.4) 계약에서는 이런 일이 일어나지 않는다** — 어떤 슬롯 값 조합을 보내도 오버라이드가 삭제되는 경로 자체가 없다. 프론트도 "이 값 조합을 보내면 삭제된다"는 특수 케이스를 처리할 필요가 없다.

## 6부 — sparse ↔ 비sparse 전환 · 무변경 저장

### 시나리오 13. 주말에 개별 일정만 단독으로 등록

8/1(토)은 정기도 구글도 없어서 지금까지 캘린더에서 계속 생략돼 있었다. 유저 A가 가족 행사 때문에 저녁만 불가능으로 등록한다.

**② 수정**

```json
{
  "items": [
    {
      "scheduleDate": "2026-08-01",
      "slots": {
        "morningStatus": "POSSIBLE",
        "afternoonStatus": "POSSIBLE",
        "eveningStatus": "IMPOSSIBLE"
      }
    }
  ]
}
```

**③ 결과:** 8/1이 더 이상 생략되지 않고 캘린더 응답에 나타난다. 정기 일정이 하나도 없어도 개별 일정만 단독 등록이 막히지 않는다.

### 시나리오 14. 아무것도 안 바꾸면 저장 버튼 자체가 안 눌려야 한다

> **[확정] (2026-07-30):** "무변경 시 저장 버튼 비활성화" 대신 "저장 버튼을 누르면 항상 3슬롯 POSSIBLE && uncertain=false를 강제 전송하자"는 대안이 논의됐으나 **채택하지 않는다.** 정기 일정이 있는 날짜(예: 근무일이라 IMPOSSIBLE로 계산되는 날)를 열어 아무것도 안 바꾸고 저장만 눌러도 정기 정보가 사라지고 "하루 종일 가능"으로 덮어써지는 데이터 무결성 문제가 있고, O1.4는 삭제 경로가 없어(시나리오 11) 그 값이 영구 고정되기 때문이다. 아래 원래 시나리오(무변경 시 저장 버튼 비활성화)를 그대로 유지한다. 트래커: [#2](https://github.com/Central-MakeUs/TripFit-server/issues/2)

정기·개별·구글이 전부 없는 날짜(예: 8/2)를 열어 아무것도 안 건드리면, 화면상 변경사항(diff)이 없다.

**캘린더 UI 규칙:** 이런 경우 저장 버튼을 **비활성화**해서 `PATCH` 자체가 안 나가게 해야 한다. 서버에는 "빈 변경을 저장"하는 개념도, "삭제"하는 경로도 없으므로 굳이 API를 호출할 이유가 없다.

## 7부 — 에러가 나야 하는 경우 (프론트 방어 코드용)

### 시나리오 15. 같은 날짜를 아이템 두 개로 나눠 보냄 → 400

```json
{
  "items": [
    {
      "scheduleDate": "2026-08-03",
      "uncertain": true
    },
    {
      "scheduleDate": "2026-08-03",
      "slots": {
        "morningStatus": "POSSIBLE",
        "afternoonStatus": "POSSIBLE",
        "eveningStatus": "POSSIBLE"
      }
    }
  ]
}
```

**결과:** `400 INVALID_INPUT`. 같은 `scheduleDate`가 배열에 두 번 오면 서버는 어느 걸 최종값으로 써야 할지 판단하지 않는다 — 애초에 `slots`와 `uncertain`을 한 아이템에 같이 담을 수 있으므로(시나리오 6), 이렇게 나눠 보낼 이유가 없다.

### 시나리오 16. `slots`도 `uncertain`도 안 보냄 → 400

```json
{
  "items": [
    {
      "scheduleDate": "2026-08-03"
    }
  ]
}
```

**결과:** `400 INVALID_INPUT`. 뭘 바꾸라는 요청인지 알 수 없다.

### 시나리오 17. `slots`를 보내면서 3개 중 하나를 빠뜨림 → 400

```json
{
  "items": [
    {
      "scheduleDate": "2026-08-03",
      "slots": {
        "morningStatus": "POSSIBLE",
        "afternoonStatus": "POSSIBLE"
      }
    }
  ]
}
```

**결과:** `400 INVALID_INPUT`. `slots` 필드를 보내는 순간 아침/오후/저녁 3개 전부 필수다 — "일부만 보내면 그 슬롯만 바뀐다"는 동작은 없다(시나리오 2 설명 참고).

### 시나리오 18. `items`가 빈 배열

```json
{
  "items": []
}
```

**결과:** `400 INVALID_INPUT`.

## 요약 — 프론트가 꼭 기억해야 할 5가지

1. **슬롯을 하나라도 바꾸려면 `slots` 안에 3개 전부** 담아 보낸다 — 나머지는 화면에 지금 보이는 값 그대로.
2. **`uncertain`은 슬롯과 별개의 필드**다. `uncertain`만 바꿀 땐 `slots` 자체를 안 보낸다. `uncertain`이 켜져 있는 동안 슬롯 오버라이드는 사라지지 않고 그대로 보존된다.
3. **한 번 저장한 날짜는 정기 패턴이 나중에 바뀌어도 안 따라간다.** 되돌리는 버튼·API는 없다.
4. **개별 오버라이드를 삭제하는 방법은 없다.** 어떤 슬롯 값 조합을 보내도(심지어 정기값과 우연히 같아도) 오버라이드는 삭제되지 않는다.
5. **정기도 개별도 구글도 없는 날짜는 캘린더 응답에서 통째로 생략된다(sparse)** — "미입력"으로 그려야지, "가능"으로 오해하면 안 된다.
