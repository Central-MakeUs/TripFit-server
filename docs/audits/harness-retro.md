# 하네스 회고 백로그

세션을 마치며 드러난 **하네스 자체의 개선 후보**를 쌓는 파일이다. 규칙이 못 걸러낸 실수, 건너뛰게 된 게이트, 훅으로 승격할 만한 반복이 대상이다. [`retro`](../../.claude/skills/retro/SKILL.md) 스킬이 G4 회고 게이트에서 만든다.

**여기 있는 것은 아직 반영되지 않은 후보다.** 항목을 실제로 `.claude/rules/`·`AGENTS.md`에 반영하려면 별도 승인이 필요하고, 반영한 뒤에는 그 항목에 반영 날짜를 적는다.

도메인 코드 감사(`{domain}/audit.md`)와 축이 다르다. 그쪽이 **구현 코드**를 점검한다면 여기는 **에이전트를 통제하는 장치**를 점검한다. 도메인 축이 아니므로 이 폴더 루트에 둔다.

## 무엇을 남기고 무엇을 남기지 않는가

범위가 겹치면 같은 내용이 여러 곳에 쌓인다.

| 남긴다 | 남기지 않는다 |
|--------|---------------|
| 규칙이 못 잡은 실수 · 건너뛴 게이트 · stale 문서로 인한 오답 | 코드·설계 개선 (`core-followup.md` 후속 제안) |
| 2회 이상 반복된 지적 | 1회성 실수 · 개인 취향 |
| 훅으로 승격 가능한 결정론적 패턴 | 다음 이슈로 미룰 기능 범위 (`defer` 스킬) |

## 항목 형식

날짜별로 아래 형식을 **위에 추가**한다(최신이 위). 각 후보에는 이번 세션의 어느 지점에서 나왔는지를 반드시 붙인다.

```markdown
## YYYY-MM-DD — 세션 주제

### 후보 1: (한 줄 제목)

- **무엇이 문제였나:** 어떤 상황에서 무엇이 잘못됐는지
- **어느 층으로:** 규칙 / 스킬·에이전트 / 훅 / 문서 SSOT
- **근거:** 이번 세션의 구체적 지점
- **제안:** 어떻게 고칠지 (선택 — 방향이 정해졌을 때만)
- **상태:** 아래 세 값 중 하나
```

`상태`는 다음 세 가지만 쓴다. 한 후보가 여러 조치로 갈라지면 상태를 섞어 적지 말고 **후보를 쪼갠다.**

| 값 | 의미 |
|----|------|
| `미반영` | 아직 아무것도 하지 않음 |
| `부분 반영 — <한 일>` | 일부만 처리됨. 남은 조치를 함께 적는다 |
| `반영 YYYY-MM-DD — <파일명>` | 완료. 어디에 반영했는지 남긴다 |

아래부터 실제 항목이다. 최신이 위로 온다.

## 2026-10-19 — 장애 알림·AI 리포트 상담과 `#126` 스펙 재작성

"동료의 모니터링 아이디어가 TripFit에 있는가"라는 질문에서 시작해, 계획 수립 → `specify`로 스펙 2개 작성 → `#126` 이슈 재작성까지 이어진 세션이다. 스펙은 `docs/specs/cross-cutting/add-prometheus.md`(Prometheus 수치 수집·기준값 알림)와 `incident-ai-report.md`(알림을 받아 수치·로그·코드를 모아 AI 원인 리포트를 Discord로 보내는 **리포터**)다. 사용자 정정이 여러 번 있었고, 아래 7건은 그 정정 지점에서 나왔다.

### 후보 1: 조사·상담·계획 응답에는 "불확실하면 질문"이 걸리지 않는다

- **무엇이 문제였나:** STOP §1.4("불확실하면 질문")와 G2 승인 질문은 문맥상 구현·스펙 단계에 묶여 있다. "이게 있어?", "계획 세워줘" 같은 대화에서는 에이전트가 추측으로 단정하고 넘어갔다.
- **어느 층으로:** 규칙
- **근거:**
  - 사용자가 개인 설정에 등록해 둔 자료("피그마 이력서")를 언급했는데, 에이전트가 그 자료를 찾지 못하자 링크를 묻지 않고 다른 자료(노션 이력서 구버전)를 대신 읽었다.
  - 계획 요청에 질문 없이 결정 5개를 한꺼번에 제시했고, 그 응답에는 계획 본문조차 빠져 있었다.
- **제안:** `core-guardrails.md` §1.4의 적용 범위에 "조사·상담·계획 응답"을 명시한다. 대상 자료를 특정할 수 없으면 다른 자료로 대신하지 말고 먼저 묻는다.
- **상태:** 미반영

### 후보 2: "한 번에 하나씩 묻기" 규칙이 없다

- **무엇이 문제였나:** 규칙은 "질문하라"까지만 정하고 묻는 방식은 정하지 않는다. 그래서 여러 결정을 묶어서 던졌다.
- **어느 층으로:** 규칙 (+ `specify` 스킬)
- **근거:** 사용자가 "하나씩 질문하면서 확인해"라고 지시한 뒤 한 개씩 묻자, 답마다 전제가 바뀌었다 — 로컬만 → 운영까지, Spring Boot → 순수 Java, 리포터 서버 사양, 운영 기준값 관찰 방식. 묶어서 물었다면 놓쳤을 전환이다.
- **제안:** `core-tools.md` G2와 `specify` 4단계에 "`AskUserQuestion`은 결정 1개씩 묻고, 답을 반영해 다음 질문을 다시 짠다. 답이 선택지 밖이면 그 답부터 처리한다"를 추가한다.
- **상태:** 미반영

### 후보 3: STOP §1.5는 저장소 밖 운영 설정을 다루지 않는다

- **무엇이 문제였나:** STOP §1.5("미구현 단정 전 코드 확인")를 지켰는데도 틀렸다. Grafana 알림처럼 운영 서버에 API로 직접 만든 설정은 코드에 흔적이 없어, 규칙 자체에 빈틈이 있다.
- **어느 층으로:** 규칙
- **근거:** 저장소·전 브랜치·이슈를 grep하고 "Grafana → Discord 실시간 에러 알림은 미구현"이라 답했다. 사용자가 실제 Discord 알림을 보여준 뒤 과거 세션 기록에서 2026-08-26 설정(Grafana 알림 규칙 4개, 연락처 `tripfit-discord-alerts`)을 찾았다.
- **제안:** §1.5에 "Grafana 대시보드·알림 등 운영 서버에 직접 만든 설정은 저장소에 없을 수 있다. 과거 세션 기록·운영 조회·사용자 확인 없이 '없다'고 단정하지 않는다"를 추가한다.
- **상태:** 미반영

### 후보 4: 운영 서버에 직접 만든 설정을 문서에 남기는 규칙이 없다

### 후보 6: G1 리서치가 설계 추천에는 걸리지 않는다

## 2026-09-04 — `retro` 스킬·`spring-reviewer` 에이전트 신설

`oh-my-yongcheol` 플러그인 구성을 참고해 하네스에 스킬 1개·서브에이전트 1개를 추가한 세션. 아래 4건은 그 과정에서 드러났고, 3건은 **새 에이전트가 자기 지침을 비판하도록 시킨 스모크 테스트**에서 나왔다.

### 후보 1: 서브에이전트 등록은 즉시가 아니다 — 문서가 단언하고 있음

- **무엇이 문제였나:** `.claude/rules/README.md`가 "**에이전트는 파일을 만들면 같은 세션에서 즉시 등록**된다(2026-09-03 실측 정정)"고 단언한다. 그런데 이날 `spring-reviewer.md`를 만든 뒤 호출은 **두 번 연속 `Agent type not found`로 실패**했고, 수 분이 지난 뒤에야 등록됐다. 같은 세션에서 `retro` **스킬은 파일 생성 즉시 등록**됐으므로, 스킬과 에이전트의 등록 시점이 다르다.
- **어느 층으로:** 문서 SSOT
- **근거:** 이번 세션에서 `Agent` 호출 2회 실패 → 파일 수정 작업 몇 건 후 등록 완료. 프론트매터는 작동 중인 `doc-reviewer.md`와 구조가 동일해 형식 문제가 아님을 확인함.
- **제안:** "즉시 등록"을 "스킬은 즉시, **에이전트는 수 분 지연될 수 있다** — 첫 호출이 실패하면 다른 작업을 하다가 재시도한다"로 정정.
- **상태:** 미반영

### 후보 2: 지침에 목록을 하드코딩하면 드리프트한다 (ArchUnit 7 vs 실제 8)

- **무엇이 문제였나:** `.claude/rules/spring-boot-java.md`가 ArchUnit 검증 규칙을 **7개 나열**하는데 `ArchitectureTest.java`에는 `@Test`가 **8개** 있다 — `commonPackageDoesNotDependOnOtherDomains`가 빠져 있다. 새 에이전트 지침에 이 목록을 그대로 옮겨 적었다가 같은 오류를 복제했고, 스모크 테스트에서 에이전트가 직접 잡아냈다. 목록이 **테스트·규칙·에이전트 세 곳**에 흩어져 갱신 지점이 셋이다.
- **어느 층으로:** 문서 SSOT (+ 규칙)
- **근거:** `grep -c '@Test' ArchitectureTest.java` = 8, `spring-boot-java.md:19` 나열 = 7.
- **제안:** 목록 하드코딩을 그만두고 **`ArchitectureTest.java`의 `@Test` 메서드명을 읽는 방식**으로 통일한다. `spring-reviewer`는 이미 그렇게 만들었으므로, `spring-boot-java.md`도 같은 방식으로 바꾸면 갱신 지점이 테스트 하나로 줄어든다.
- **상태:** 미반영

### 후보 3: 읽기 전용 에이전트의 쓰기 차단은 도구 목록으로 완결되지 않는다

- **무엇이 문제였나:** 세 에이전트 지침과 문서 3곳이 "`Edit`/`Write` 도구가 **없어서 파일을 고칠 수 없다**"고 서술했으나, 셋 다 `tools`에 **`Bash`가 있어** `sed -i`·리다이렉션으로 얼마든지 수정 가능하다. 게다가 `auto-format-java.sh` 훅은 `Edit|Write` 매처라 **Bash 경유 수정은 감지조차 못 한다.** 안전장치를 실제보다 강하게 믿고 있던 상태였다.
- **어느 층으로:** 훅 (문서 정정은 이번 세션에 이미 반영)
- **근거:** `grep '^tools:' .claude/agents/*.md` → 셋 다 `Bash` 포함. 스모크 테스트에서 에이전트가 자기 지침의 이 문장을 직접 지적함.
- **제안:** `deny-dangerous-bash.sh`에 읽기 전용 에이전트 컨텍스트의 파일 쓰기 패턴(`sed -i`, `>` 리다이렉션, `tee`, `git checkout/restore`)을 추가한다. **exit code로 판정 가능하므로 훅 조건을 만족**한다 — 지금처럼 규범에만 의존하면 이 층은 통제가 아니라 부탁이다.
