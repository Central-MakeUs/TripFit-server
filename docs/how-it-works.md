# 지금 이렇게 동작합니다

기술을 잘 모르는 사람도, 오래 안 봐서 까먹은 사람도, "지금 이 순간 이 기능이 실제로 어떻게 동작하는지"를 이 문서 하나만 보고 알 수 있게 하기 위한 문서입니다.

**이 문서가 아닌 것:**
- 스펙·ADR이 아닙니다 — "왜 이렇게 결정했는지"의 논의 과정·후보안 비교는 각 절 끝 "더 자세히" 링크를 따라가세요.
- 변경 이력이 아닙니다 — 과거에 어땠는지가 아니라 **지금** 어떤지만 담습니다. 로직이 바뀌면 이 문서도 그 자리에서 바로 고쳐 쓰고, 예전 방식은 지웁니다.
- 글쓰기 스타일은 [`.claude/rules/core-reporting.md`](../.claude/rules/core-reporting.md)를 따릅니다 — 용어를 풀어쓰고, 결과 중심으로 설명합니다.

**갱신 규칙:** 인증·결제·데이터 저장 방식처럼 보안·아키텍처 성격이 있는 로직을 바꾸면, 그 작업과 **같은 턴**에 이 문서의 해당 절도 고칩니다 (`.claude/rules/core-guardrails.md` ⛔ STOP §6).

**차례**

- 전체 그림 — [기술 스택](#기술-스택-한눈에) · [코드 구조](#코드-구조-아키텍처) · [테스트](#테스트는-이렇게-합니다) · [배포·운영](#배포운영-구조)
- 기능별 동작 — [로그인·세션](#로그인세션-인증) · [여행방 생명주기](#여행방-생명주기-상태) · [알림 발송](#알림-발송) · [Google Calendar 연동](#google-calendar-연동) · [일정·휴가 정책](#일정휴가-정책) · [여행 날짜 추천](#여행-날짜-추천)

## 기술 스택 한눈에

이 서버는 자바(Java 21)로 짜여 있고, 스프링 부트(Spring Boot)라는 프레임워크 위에서 돌아갑니다. 데이터는 두 군데에 나눠 저장합니다 — 대부분의 데이터(사용자, 여행방, 일정 등)는 MySQL이라는 관계형 데이터베이스에, 자주 바뀌고 빨리 읽어야 하는 데이터(리프레시 토큰, 공휴일 캐시)는 Redis라는 메모리 기반 저장소에 둡니다.

로그인은 구글·카카오·애플 소셜 로그인만 지원하고, 서버가 자체적으로 비밀번호를 저장하지 않습니다(아래 로그인·세션 절 참고). API 문서는 Swagger(OpenAPI)로 자동 생성되고, 코드 위에 적어둔 설명(Javadoc)이 그대로 문서에 반영됩니다. 푸시 알림은 구글의 FCM(Firebase Cloud Messaging)을 씁니다.

**왜 이렇게 만들었는지:** 팀 규모가 크지 않은 초기 단계라, 복잡한 인프라보다는 검증된 조합(Spring Boot + MySQL)을 우선 골랐습니다. Redis는 나중에 "빠르게 자주 바뀌는 데이터"가 늘면서 추가됐습니다.

## 코드 구조 (아키텍처)

코드는 기능(도메인) 단위로 폴더가 나뉘어 있습니다 — 로그인(`auth`), 사용자(`user`), 여행방(`trip`), 알림(`notification`) 등. 각 도메인 폴더 안은 다시 역할별로 나뉩니다.

- **controller** — 요청을 받고 응답을 돌려주는 창구. 여기엔 비즈니스 로직을 두지 않습니다.
- **service** — 실제 처리 로직. "일정 확인을 끝내야 방에 들어갈 수 있다" 같은 규칙이 여기 있습니다.
- **domain** — 데이터의 모양(사용자, 여행방 등)을 정의하는 곳.
- **repository** — DB에서 데이터를 읽고 쓰는 곳.

이 구조 규칙 중 일부(예: "데이터 정의 코드는 요청 처리 코드를 몰라야 한다")는 사람이 글로만 정해둔 게 아니라, **테스트를 돌릴 때마다 기계적으로 자동 검사**됩니다 — 규칙을 어기면 그 자리에서 테스트가 실패합니다.

**왜 이렇게 만들었는지:** 정식 DDD(도메인 주도 설계)만큼 무겁게 가져가진 않지만, "이 코드가 무슨 일을 하는 코드인지" 폴더 이름만 보고 알 수 있게 하려는 최소한의 구조입니다.

**더 자세히:** [`architecture.md`](architecture.md)

## 테스트는 이렇게 합니다

테스트는 크게 두 종류로 나뉩니다.

- **단위 테스트** — DB 없이, 코드 하나(예: 서비스 클래스 하나)의 로직만 따로 확인합니다. 빠릅니다.
- **통합 테스트** — 실제로 MySQL을 하나 띄워서(Testcontainers라는 도구가 테스트를 실행하는 동안만 임시 DB를 켰다 끕니다) DB까지 포함한 전체 흐름이 맞는지 확인합니다.

여기에 더해 **코드 구조 자체를 검사하는 테스트**도 있습니다(ArchUnit) — "컨트롤러가 DB 접근 코드를 직접 부르면 안 된다", "모든 테이블의 ID는 특정 형식(UUID)이어야 한다" 같은 규칙 8가지를 코드 전체를 스캔해서 자동으로 확인합니다. 사람이 리뷰하다 놓칠 수 있는 구조 위반도 여기서 걸러집니다.

**언제 돌아가는지:** 로컬에서 언제든 실행할 수 있고(`./gradlew test`), 깃허브에 코드를 올릴 때마다(GitHub Actions) 자동으로도 돌아갑니다 — 테스트가 하나라도 실패하면 그 변경사항은 배포되지 않습니다.

**왜 이렇게 만들었는지:** 사람이 매번 "이 구조 규칙을 지켰나?"를 눈으로 확인하는 건 실수가 나기 쉬워서, 지킬 수 있는 규칙은 최대한 기계가 검사하게 만들었습니다.

**더 자세히:** `.claude/rules/testing.md`

## 배포·운영 구조

이 서버는 클라우드(AWS)의 서버 4대에 역할을 나눠서 올라가 있습니다 — 하나에 문제가 생겨도 나머지는 영향받지 않게 하기 위해서입니다.

- **서버 1** — 실제 API 서버(Spring Boot)와, 요청을 받아 그쪽으로 전달해주는 문지기(Nginx)
- **서버 2** — MySQL 데이터베이스 전용
- **서버 3** — 운영 상태를 지켜보는 모니터링 도구(Grafana) — 서버 1·2의 로그를 모아서 볼 수 있게 해줍니다
- **서버 4** — Redis 전용

코드를 깃허브에 올리고 정식 브랜치(`main`)에 반영되면 자동으로 다음이 일어납니다 — (1) 테스트 전체 실행 → (2) 통과하면 배포용 이미지를 만들어 저장 → (3) 서버 1에 새 버전을 올림. 이 과정에서 **API 계약이 예고 없이 바뀌지 않았는지도 자동으로 검사**해서, 프론트가 대응해야 하는 변경이면 Discord로 알림이 갑니다.

**왜 이렇게 만들었는지:** 서버 역할을 분리해두면, 예를 들어 모니터링 서버에 문제가 생겨도 실제 서비스(API)는 멈추지 않습니다. API 계약 변경 자동 감지는 "필드 하나 추가했을 뿐인데 프론트가 모르고 있었다" 같은 사고를 막기 위한 장치입니다.

**더 자세히:** [`../deploy/README.md`](../deploy/README.md)

## 로그인·세션 (인증)

사용자가 구글·카카오·애플 계정으로 로그인하면 서버는 토큰 두 개를 내려줍니다 — 접속을 확인하는 데 쓰는 "액세스 토큰"과, 그게 만료됐을 때 새로 발급받기 위한 "리프레시 토큰"입니다.

- **액세스 토큰**은 앱(클라이언트) 메모리에만 있고 유효기간은 15분입니다. 앱을 껐다 켜면 사라지고, 리프레시 토큰으로 다시 받아야 합니다.
- **리프레시 토큰**은 응답 JSON 안에 넣지 않고, 브라우저·앱이 자동으로 관리하는 쿠키(HttpOnly)로만 전달됩니다 — 자바스크립트 코드가 이 값을 직접 읽을 수 없어서, 악성 스크립트가 페이지에 껴도 토큰을 훔쳐갈 수 없습니다. 서버 쪽 저장소는 MySQL이 아니라 Redis(빠른 임시 저장소)이고, 유효기간은 30일입니다.
- 리프레시 토큰으로 재발급을 받을 때마다 기존 토큰은 폐기되고 새 토큰으로 교체됩니다. 이미 폐기된 토큰이 다시 쓰이면 "누가 훔쳐서 쓰는 것"으로 간주해 그 로그인 체인 전체를 강제 로그아웃시킵니다.
- 액세스 토큰은 서버가 "이 토큰은 무효"라고 따로 기록해두는 블랙리스트가 없습니다 — 그래서 로그아웃을 눌러도 이미 발급된 액세스 토큰은 남은 시간(최대 15분) 동안은 여전히 유효할 수 있습니다. 그 대신 유효기간 자체를 짧게 잡아서 위험을 줄였습니다.

**왜 이렇게 만들었는지:** 원래는 리프레시 토큰도 액세스 토큰처럼 JSON 응답으로 내려줘서 앱이 직접 저장했는데, 새로고침하면 그 값이 통째로 사라지는 버그가 있었습니다(2026-08-17 사용자 신고로 발견). 조사 과정에서 "값을 JSON으로 내려주고 클라이언트가 알아서 저장하게 하는 방식 자체가 잃어버리기도 쉽고 탈취에도 약하다"는 결론에 이르러, 지금 방식(쿠키+Redis)으로 통째로 바꿨습니다.

**더 자세히:** [`specs/auth/auth-refresh-redis-cookie.md`](specs/auth/auth-refresh-redis-cookie.md) · [`decisions/010-redis-infra.md`](decisions/010-redis-infra.md)

## 여행방 생명주기 (상태)

여행방에는 두 가지 "상태"가 동시에 있습니다 — **방 전체**의 상태와, 그 방에 속한 **각 멤버 개인**의 상태입니다.

**방 전체 상태:**
- **조율 중(ONGOING)** — 날짜를 아직 못 정하고 다 같이 맞춰보는 중. 새로 참여할 수 있고, 방 정보 수정·일정 확인·추천(구현 예정)도 할 수 있습니다.
- **일정 확정(CONFIRMED)** — 방장이 날짜를 확정한 뒤. 이제 새로운 사람은 이 방에 못 들어옵니다.
- **종료(EXPIRED)** — 여행 희망 기간이 다 지나면 자동으로 이 상태가 됩니다. 기존 멤버 조회만 가능합니다.

**멤버 개인 상태:**
- **일정 확인 대기중(SCHEDULE_PENDING)** — 방장이든 참여자든 방에 막 들어온 직후 상태입니다. 자기 일정을 확인해서 "확인 완료"를 눌러야 다음 단계로 넘어갑니다.
- **방 활동 가능(ACTIVE)** — 일정 확인을 끝낸 상태입니다. 이때부터 방 상세·멤버 목록·달력을 볼 수 있고, 방장이면 초대 링크도 공유할 수 있습니다.

**왜 이렇게 나눴는지:** "방에 들어왔다"와 "실제로 이 방을 쓸 준비가 됐다"를 구분해야, 자기 일정도 확인 안 하고 무작정 들어온 사람이 바로 초대 링크를 다른 사람에게 뿌리는 것 같은 상황을 막을 수 있습니다.

**더 자세히:** [`product/glossary.md`](product/glossary.md) · [`specs/trip/trip-member-status-derive.md`](specs/trip/trip-member-status-derive.md)

## 알림 발송

방 안에서 중요한 일(모든 멤버가 일정을 다 냈다, 날짜가 확정됐다, 확정이 취소됐다 등)이 생기면, 서버는 이걸 먼저 "이벤트"로만 표시해두고, 그 작업이 DB에 완전히 저장되고 나서야(트랜잭션 커밋 후) 알림을 실제로 내보냅니다. 저장 도중 뭔가 실패해서 롤백되면 알림은 아예 나가지 않습니다.

알림은 FCM(구글의 푸시 서비스)으로 실제 기기에 보내는 것과, 앱 안 "알림센터"에 이력을 남겨두는 것을 같이 합니다.

**왜 이렇게 만들었는지:** 알림 발송(외부 서비스 호출)이 느려지거나 실패해도 그것 때문에 방금 완료된 원래 작업까지 실패한 것처럼 보이면 안 되기 때문에, "DB에 저장하기"와 "알림 내보내기"를 완전히 분리했습니다. 반대로 저장이 실패(롤백)했는데 알림만 먼저 나가버리는 것도 막아야 해서, 알림은 항상 저장이 확실히 끝난 뒤에만 나갑니다.

**더 자세히:** [`specs/notification/notification.md`](specs/notification/notification.md)

## Google Calendar 연동

사용자가 구글 캘린더 연결을 허용하면, 서버는 구글 API로 "이 시간대에 바쁜지 아닌지"만 확인해서 가져옵니다 — 일정 제목이나 내용까지는 가져오지 않습니다. 이 정보는 날짜별 캐시 테이블에 저장해두고, **30분마다 자동으로** 연동된 모든 사용자를 다시 동기화합니다. 한꺼번에 몰아서 확인하면 구글 쪽 호출 제한에 걸릴 수 있어서, 사용자 한 명씩 확인할 때마다 짧게(0.1초) 간격을 둡니다.

구글이 발급한 토큰은 암호화해서 저장하고, 구글 서버와 통신하는 동안은 DB 접속 자리를 붙잡지 않도록, 통신이 다 끝난 뒤 결과만 짧게 저장합니다(로그인 절의 원리와 동일).

**왜 이렇게 만들었는지:** 실제 일정 내용까지 가져오면 필요 이상으로 개인정보를 모으는 셈이라 "바쁨/안 바쁨"만 가져옵니다. 자동 재동기화 간격을 30분으로 둔 건 "실시간까지는 아니어도 크게 뒤처지지 않게"와 "구글 API를 너무 자주 호출하지 않게"의 절충입니다.

**더 자세히:** [`specs/user/google-calendar-oauth.md`](specs/user/google-calendar-oauth.md)

## 일정·휴가 정책

사용자의 "이 날짜에 시간이 되는지"는 아래 네 가지 정보를 합쳐서 계산합니다.

1. **정기 일정** — 매주 반복되는 출근·수업·회의 같은 것. 요일과 시간대별로 가능/불가능을 등록합니다.
2. **개별 일정** — 특정 날짜 하나만 예외로 덮어쓰는 일정(정기 일정과 다르게 그날만 바쁘거나, 반대로 그날만 비는 경우).
3. **공휴일** — 외부 공공 API에서 가져와 서버에 캐싱해두고, 스케줄러가 주기적으로 최신 상태를 유지합니다.
4. **Google Calendar 연동 정보** — 바로 위 절.

이 네 가지를 합쳐서 날짜별로 가능/불가능 여부를 보여주고, 아무 정보도 없는 날은 기본적으로 "가능"으로 취급합니다.

별개로 **연차 신청 정책**이라는 값도 있습니다 — "여행을 가려면 회사에 연차를 얼마나 미리 신청해야 하는지"(언제든 가능 / 1주 전 / 2주 전 / 1달 전)를 사용자가 미리 등록해두는 값으로, 나중에 여행 날짜를 추천할 때 "이 사람이 실제로 이 날짜에 연차를 낼 수 있는가"를 계산하는 데 씁니다.

**왜 이렇게 만들었는지:** 네 가지 정보 소스를 각각 독립적으로 관리하고 실제 조회하는 시점에만 합칩니다 — 그래야 정기 일정 하나를 바꿀 때마다 구글 캘린더 데이터를 다시 가져오는 것 같은 불필요한 연쇄 작업이 없습니다.

## 여행 날짜 추천

방장이 날짜 추천을 요청하면, 서버는 후보 날짜마다 점수를 매겨서 순위를 매깁니다. 점수는 네 가지를 조합해서 계산합니다 — **아예 못 오는 사람의 비율**, **일부만 참석 가능한 사람의 비율**, **아직 일정이 확실하지 않은 사람의 비율**, **그 날짜에 필요한 연차 일수**.

방장은 이 네 가지 중 뭘 더 중요하게 볼지 "추천 모드"로 고를 수 있습니다 — 예를 들어 "휴가 아끼기" 모드를 고르면 연차 일수를 가장 무겁게 반영하고, "모두 참석" 모드를 고르면 못 오는 사람 비율을 가장 무겁게 반영합니다.

방장이 추천 후보 중 하나를 **확정**하면, 그 시점의 멤버 일정을 그대로 사본으로 떠서(스냅샷) 별도로 저장해둡니다 — 확정 이후에 누군가 자기 정기 일정을 바꾸더라도, "그때는 이런 근거로 이 날짜를 정했다"는 기록이 사라지지 않습니다. 방장은 확정을 취소할 수도 있는데, 이때는 취소 사유(새 일정이 생겼다, 참석 인원이 바뀌었다 등)를 반드시 남겨야 합니다.

**왜 이렇게 만들었는지:** 방장마다 중요하게 여기는 기준이 다르기 때문에(전원 참석이 중요한 사람도, 연차를 아끼는 게 중요한 사람도 있음) 점수 계산 방식 자체를 고를 수 있게 했습니다. 스냅샷을 뜨는 이유는, 확정 후에 개인 일정이 바뀌어도 "왜 이 날짜로 정했는지"에 대한 근거가 조용히 사라지지 않게 하기 위해서입니다.
